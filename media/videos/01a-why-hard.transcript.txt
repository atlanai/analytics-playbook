Pilots don't stall on the demo. They stall on the tenth real question. It touches two tables and a house rule... and the answer comes back confident, and wrong. This is why analytics agents are hard... and the four problems that follow.

Every question your agent answers goes through five steps. Intent. Context. SQL. Execute. Insight. Writing the SQL is easy, once the agent knows what the question means. Knowing what it means... that's the open problem.

Take one question... what's our Q3 sales pipeline? The query gets the fiscal quarter right, and it returns $18.4 million. Now add one line... and it's $11.2 million. That's the number Finance plans on. No bug here. That rule just isn't in any table, column, or description.

That rule is one of five decisions hiding in this question. Which stages count? Which rows are always out? Which quarter, and which amount, on which table? And how do the rows get put together? Guess each one right 80% of the time... and you'll get all five right about one time in three. That's just arithmetic. On bare schema, only the tables, we measured 31.8%.

So is it the model? We ran the same questions on five models, with bare schema. They landed between 31.8% and 42.1%. Then we gave them past SQL as context... and every model we ran scored above 66%. Switching models moved the score about 10 points. Adding context moved both paired models 26 or more. Next year's model will guess better. It still won't know that your Finance team drops the earliest stages.

Once a rule is written down, its form decides whether the agent follows it. As a sentence, the agent has to turn it into SQL on every question... and every translation is another guess. As SQL, the decision is made once, and it runs the same way every time. On multi-table questions, the same metric as SQL beat the sentence by 16 points.

And the last problem... how do you know it's right? Without a fixed test, a sponsor sees three good answers in a demo, and believes it works. A builder changes a prompt, tries two questions, and believes it improved. Both are guessing. And one run doesn't settle it. The same setup, run twice, moved by 6 questions.

So that's four problems. A clean query returns the wrong number. The question hides decisions the schema doesn't show. The agent decides differently each time. And nobody can tell whether it's right. The rest of this playbook fixes each one.

So the tenth question never needed a bigger model. It needed the missing rule. Fix the context before you change the model. Next up: The method at a glance. What closes the gap, and the loop that builds it.
